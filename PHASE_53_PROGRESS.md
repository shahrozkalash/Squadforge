# Phase 53 Progress — Actions and Batch Processing (Graphics Editor)

Date: 2026-11-26
Baseline: local snapshot after Phase 52 (staged locally, **not pushed** — batched push is the owner's)
Status: **Implemented and verified locally.** Extends the Phase 19/44–52 image engine in place (new module `server/imageEditor/actions.ts`, exported through the existing `index.ts`); actions are recordings of the engine's own entry points — there is no second implementation of any operation. Acceptance is the owner's decision.

## What was built

- **Action model (`ImageAction` / `ActionStep`)** — an action is plain ordered data: `{ name, steps: [{ op, params }] }`. The vocabulary (`ACTION_OPS`, listed by `listActionOps()`) has 14 operations, each naming a real engine entry point: `filter` (any Phase 47 registry filter, via `applyFilter`), the Phase 19 adjustments `brightness-contrast`, `saturation`, `invert`, `grayscale` (the direct Phase 19 functions, not the registry wrappers), layer operations `add-layer`, `fill-rect`, `set-opacity`, `set-visibility`, `set-blend-mode`, `flatten` (the engine's `composite()` collapsed into a single layer), canvas operations `resize` (`resizeProject`) and `rotate` (`rotateProject`, 90/180/270), and `export` (a snapshot of the current composite through `composite()` + `exportImage`, PNG or BMP). Layer-targeting steps name their layer **by name** — engine layer ids are per-project UUIDs and would not survive serialization or transfer to another project; an omitted `layer` means the project's active layer, which is how the editor itself behaves.
- **Total up-front validation (`validateAction` / `defineAction` / `parseAction`)** — an action is fully validated before any pixel is touched, so a bad action can never fail halfway through a replay. Structure, operation ids and per-operation parameter keys are checked strictly (unknown keys are rejected, not ignored). Filter steps are validated by the Phase 47 registry itself: `getFilterDescriptor` rejects unknown filter ids and `resolveFilterParams` rejects unknown parameter names and out-of-range values and fills schema defaults — a validated action stores the *resolved* parameter set, so replay is stable even if registry defaults ever change. Other ranges mirror the engine: opacity 0..1 (exactly `setLayerOpacity`'s own check), saturation −1..1 (the range `adjustSaturation` documents), blend mode against `BLEND_MODES` (the engine's `assertBlendMode` set), rotate restricted to the step rotations `rotateProject` supports. Brightness/contrast are validated as finite numbers only, because the Phase 19 formula genuinely accepts any finite value. Two deliberate action-layer rules are documented as such: `resize` additionally requires integers in 1..16384 (an action file may not ask the engine to allocate an unbounded canvas), and `export` names must be plain file names (no directories or traversal). Registry validation errors are rethrown with the step index and operation attached.
- **Replay (`applyAction`)** — validates, then executes the steps in order by calling the engine functions themselves; the project ends up exactly as if the operations had been performed by hand (byte-exact, tested against a hand-driven project). `export` steps do not mutate: each collects an `ActionOutput` (name, format, encoded buffer, step index) snapshotting the composite at that point in the sequence, so one action can emit a before/after pair. A step naming a layer that does not exist fails the replay with the layer named — that is a project mismatch, not an action defect, and it is the one replay-time failure validation cannot rule out.
- **Recorder (`ActionRecorder`)** — produces an action *by doing*: each method performs the operation on the wrapped live project through the engine and appends the step that reproduces it (target layers recorded by name; filter parameters recorded resolved). `exportSnapshot()` records an export step and returns the snapshot taken at that moment. A failed operation (e.g. an out-of-range filter) throws from the engine call and is never recorded. Replaying a recording on a fresh copy of the same source project reproduces the live project byte-exactly, including the exported bytes.
- **Presets** — `serializeAction` / `parseAction` are the JSON storage form; load validates, and a serialize → parse → serialize round trip is field-exact (identical text), tested.
- **Batch processing / export queue (`startBatch`)** — runs one validated action over many image files. Each input is decoded with the existing codec (`importImage`: PNG and BMP), placed as the Background layer of a fresh project (the import assignment the engine's own tests and routes use), replayed, and written to the output directory (created if missing). The written bytes are the action's **last** `export` snapshot when the action exports, else the final composite encoded as PNG. Output names derive from the input name (`<base>.edited.<ext>`), or from the caller's `outputName` callback — an export step's fixed `name` is deliberately *not* used per file, because one fixed name would make every file overwrite the previous one. Files start in input order through `concurrency` lanes (default 1, strictly sequential; more lanes may finish out of order, results stay in input order). Per-file state is tracked as `pending → running → done/failed/cancelled` with the failure's message recorded; `onProgress` fires after every file settles with an aggregate snapshot — calling `job.cancel()` from the callback is the deterministic early-stop path. Cancellation stops *new* files from starting; a file that has started always finishes (its work between filesystem awaits is synchronous engine work), and files that never started are reported `cancelled`. Per-file failures — missing file, corrupt bytes, a replay error — are recorded on that file only and never abort the batch; `job.done` resolves (never rejects for per-file failures) with the drain summary `{ total, done, failed, cancelled, results }`.

## Limitations (stated honestly)

- **The vocabulary is the listed 14 operations.** Painting (brush strokes), selections, masks, groups, transforms, content layers and Phase 52 effect stacks are not action steps in this phase — an action cannot record them, and the recorder has no methods for them. The vocabulary covers what the brief required (registry filters, Phase 19 adjustments, layer add/flatten/export, resize, PNG export settings) plus the small layer-property set; it is not a macro language for the whole editor.
- **Layer targeting is by name**, and names are not unique in the engine's model — a step resolves to the *first* layer with that name. Recordings made on projects with duplicate layer names replay against the first match. (Engine ids would be exact but are per-project UUIDs, useless in a stored preset.)
- **`export` settings are format + name only**, because that is what the codec genuinely offers: the PNG encoder's one option is an ICC profile (Phase 50), and binary profile data is not action data — actions deliberately do not carry it. BMP is offered as the second format because `exportImage` genuinely supports it.
- **Batch concurrency is bounded by synchronous engine work**: decoding, replay and encoding run on the main thread between filesystem awaits, so lanes interleave at file boundaries, not mid-image. Concurrency raises file-level parallelism (I/O overlap); it does not parallelize a single image's processing (that is Phase 51's provider seam, which the batch does not use).
- **Cancellation is between files, not mid-file** — a started file always finishes and is reported done/failed truthfully; there is no partial-output state to clean up because outputs are written once, whole, at the end of a file's processing.
- **Batch inputs are single images**, each becoming a one-layer project. Multi-layer sources (project JSON, PSD) are not batch inputs in this phase, and actions that add layers apply per file independently.
- **The generated C# desktop app and the HTTP routes do not yet expose actions or batch processing** — as with Phases 44–52, this phase covers the TypeScript engine.
