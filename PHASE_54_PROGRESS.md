## What was built

- **Workspace model (`EditorWorkspace`)** — panel layout as data: the six panels the editor genuinely has (`tools`, `layers`, `colors`, `filters`, `history`, `properties` — the first three are the panels the generated app renders; filters/history/properties are the engine's corresponding surfaces from Phases 47/52 and the engine history), each a `PanelLayout { id, dock: 'left'|'right'|'top'|'bottom', visible, weight }`. Layout operations (`setPanelVisible`, `movePanel`, `setPanelWeight`, `getPanelLayout`) validate: unknown panel ids, unknown docks and non-positive/non-finite weights are rejected with named errors. Two named presets ship: `default` (all panels visible; tools left w1, filters left w2, layers right w3, colors right w2, history right w2, properties right w2) and `focus` (same docks/weights, filters/history/properties hidden). `getWorkspacePreset` returns a fresh independent state per call — mutating one copy never leaks into the next (tested).
- **Keyboard shortcuts** — a command set of 21 commands (`EDITOR_COMMANDS`), each naming the real engine/app operation it invokes (project create/open/save and PNG export via `serializeProject`/`deserializeProject`/`exportImage`; undo/redo via `HistoryStack`; the seven `ImageTool` selections; layer add/remove/reorder via `addLayer`/`removeLayer`/`moveLayer`; canvas zoom via the engine's `zoomAt` semantics; rotate via `rotateProject`; flip via `flipImage` applied per layer). Chords are data (`KeyChord { key, ctrl, shift, alt }`) with a canonical text form (`formatKeyChord`/`parseKeyChord` round-trip; named keys, F1–F24, and the literal `+` key handled). The default map is the conventional one (Ctrl+N/O/S, Ctrl+Shift+E export, Ctrl+Z / Ctrl+Shift+Z, single-letter tool keys B/E/U/O/L/T/G, Delete for layer delete, Ctrl+] / Ctrl+[ layer order, Ctrl+= / Ctrl+− zoom, Ctrl+Shift+R rotate, Ctrl+Shift+H flip). `setShortcut` **rejects** a chord already bound to a different command, naming the holder (`Shortcut conflict: "Ctrl+Z" is already bound to edit.undo`); rebinding the owning command is a no-op, and moving a binding frees its old chord. `resolveShortcut` matches a key-event-like object with **modifier exactness** — Ctrl+Shift+Z resolves to redo and never to the Ctrl+Z undo binding, a plain-letter tool binding does not fire with Ctrl held, and un-canonicalizable event keys resolve to `null` rather than throwing. Shortcut maps serialize/deserialize with unknown commands, malformed chords and duplicate chords all rejected.
- **Guides, grid, snapping (project data + pure functions)** — `ImageProject` gained `guides: GuideLine[]` (`{ orientation: 'horizontal'|'vertical', position }`) and `grid: GridSettings` (`{ spacingX, spacingY, offsetX, offsetY }`, default 16/16/0/0), persisted through the existing v2 format as **optional fields** (the Phase 48/52 pattern): written by `serializeProject`, validated on load (bad orientation, non-finite position, non-positive spacing and non-finite offsets are rejected with named errors), and absent fields load as the defaults, so pre-Phase-54 files open unchanged. Guide operations (`addGuide`, `moveGuide`, `removeGuide`, `clearGuides`) are bounds- and value-checked; `setGridSettings` validates and stores a copy. Snapping is pure: `snapCoordinate(value, axis, project, options)` and `snapPoint` consider, per axis, the guide positions on that axis, the canvas edges and center (0, size/2, size), and the nearest grid line. **Priority rule (stated and tested): the closest candidate within the threshold wins; on an exact distance tie the order is guide, then canvas, then grid.** The threshold (default 8 px) is inclusive; each source family can be disabled per call; non-finite values and negative thresholds throw.
- **Tool settings + color panel state (`WorkspaceToolState`)** — the active tool (validated against the engine's `ImageTool` union), the Phase 46 brush settings (every write goes through `createBrushSettings`, so the Phase 46 validators reject bad sizes/opacities — there is no second validation), and foreground/background colors validated as real engine `RgbaColor`s (every channel finite, 0..255), with `swapColors` and `resetColors` (black over white defaults). The tool state is persisted **with** the workspace: `serializeWorkspace`/`deserializeWorkspace` round-trip panels + shortcuts + tool state field-exactly (identical re-serialized JSON, tested), and corrupt forms are rejected one by one (bad format tag, unknown/duplicate/missing panel, bad dock, bad weight, unknown shortcut command, conflicting chords, bad color channel, unknown tool, invalid brush values). The brush is stored in the file via the Phase 46 preset serializer's settings shape, so a stored workspace brush is exactly a brush preset's settings.
- **Generated desktop app wiring (through the generator, never by editing output)** — `ImageProjectGenerator` now emits a new `Workspace.cs` whose contents are **generated from the TS model**: `PanelLayoutEntry` records for both presets' layouts and the full shortcut dictionary (command id → chord string) come from `createDefaultWorkspace()`/`createFocusWorkspace()` at generation time, plus a `ShortcutResolver` that canonicalizes a WinForms `KeyEventArgs` (letters/digits via the `Keys` enum, Delete, `OemOpenBrackets`/`OemCloseBrackets` for `[`/`]`, `Oemplus`/`OemMinus` for `=`/`-`, modifiers from the event) into the same chord string form and looks it up — modifier-exact, mirroring the TS resolver. `MainForm` was refactored inside the generator: it docks its tools strip, colors bar and layer side panel **from `WorkspaceData.DefaultLayout`** (dock side, visibility, and side-panel width = weight × 70 px), sets `KeyPreview = true`, and dispatches `OnKeyDown` through `ShortcutResolver` to named methods (`NewProject`, `OpenProject`, `SaveProject`, `AddLayer`, `DeleteLayer`, `MoveLayerUp`, undo/redo, export, rotate, flip) — the menu items call the same methods and display their chords via `ShortcutKeyDisplayString`. The colors bar carries foreground/background pickers plus a **Swap colors** button wired to the canvas colors. Supporting additions in the generated app: `EditorCanvas.BackColor2` and `EditorCanvas.ZoomBy(factor)` (center-anchored, clamped like the wheel zoom), and `ImageDocument.RemoveLayer`/`MoveLayer` so the delete/reorder shortcuts have real operations to call. The Phase 19 test needles (`Undo()`, `ExportImage(ImageFormat.Jpeg)`) still match the generated `MainForm.cs` — asserted in the Phase 54 suite itself.
- **Accessibility position (honest)** — the testable claim is **keyboard-only operation**: every one of the 21 documented commands has exactly one default binding (asserted), resolution is modifier-exact (asserted), and the generated shell dispatches all of them from the keyboard. **Visual accessibility (contrast, scaling, screen-reader behavior) is not verified anywhere in this phase and is not claimed** — the generated GUI cannot be run on this VM (no display), so nothing about its rendered appearance is asserted.

## Limitations (stated honestly)

- **The generated GUI was never run or visually verified** — this VM has no display. The WinForms app is compile-verified only (restore + build + PE inspection through the Phase 18 pipeline). The Phase 36 `--smoke` headless mode belongs to the Phase 36 Avalonia app, not this WinForms editor, and does not apply. Panel docking, shortcut dispatch and the swap-colors button are real generated code paths, but their on-screen behavior is unverified.
- **The shell renders three of the six panels.** Tools, layers and colors exist as WinForms controls and are docked from the layout data; filters, history and properties are present in the emitted layout data (both presets) but the Phase 19 shell has no controls for them, so changing their layout entries has no visible effect in the generated app yet. The layout model itself is complete and tested in the TS engine.
- **The generated app does not load or save workspace files.** It carries the default layout + shortcut map as generated code (data, regenerated from the model on every generation); user-rebindable shortcuts and persisted custom layouts exist in the TS engine (`serializeWorkspace`) but are not wired into the C# shell in this phase.
- **Guides and grid are data + logic, not rendering.** Nothing draws guide lines, a grid overlay, or rulers in either the TS engine (which has no canvas UI) or the generated app; snapping is exposed as pure functions for callers, and no editor surface calls them yet. There are no ruler widgets in this phase.
- **Shortcut scope is the documented 21 commands.** Operations without a command id (e.g. adjustments, filters, batch) have no default binding; the coverage claim covers exactly the documented command set, nothing more.
- **Plain-letter tool shortcuts in the generated shell fire whenever the form has key preview**, including when a dialog-free control has focus; the app has no text-entry fields on its main form, so this matches its existing input surface, but it is a real behavioral property, stated here rather than discovered later.
- **Visual accessibility is unverified and unclaimed** (see above): no contrast, scaling or assistive-technology claim is made for either the model or the generated app.
