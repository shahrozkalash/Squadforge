## Requirement-by-requirement

| # | Requirement | Evidence |
| :--- | :--- | :--- |
| 1 | Grayscale as a first-class working representation alongside RGBA, Rec.601 conversion both ways, exact-value tests | New `GrayImage` type (single channel, the engine's established mask/selection representation) with `createGrayImage`/`cloneGrayImage`/`getGray`/`setGray`, `rgbaToGrayscale` (Rec.601 0.299/0.587/0.114, `Math.round` — the Phase 19 weights and rounding) and `grayscaleToRgba` (replicate + opaque) in `server/imageEditor/colorManagement.ts`. Tests pin red 76 / green 150 / blue 29 / white 255 / (10,20,30) → 18, the all-256-level gray→RGBA→gray identity, and byte-agreement with the existing Phase 19 `grayscale()` adjustment on the same pixels. This is a representation, not another adjustment wrapper: the Phase 19 adjustment is untouched and the two are proven equal. Alpha handling is explicit, not silent: conversion discards alpha and uses RGB as stored (pinned by a transparent-red → 76 test). |
| 2 | Genuine 16-bit workflow: typed-array representation, lossless 8→16 (v*257), documented 16→8 rule, a real operation in 16-bit, full-range round trip | New `PixelImage16` type (RGBA `Uint16Array`). Upscale `v * 257`; downscale `round(v / 257)` — the exact inverse for 8-bit-origin values, so 8→16→8 is byte-exact for all 256 levels (full-range test image, deep-equal). Downscale pins: 128→0, 129→1, 256→1, 32896→128, 65535→255. Two operations run natively in 16-bit: `applyGain16` (25957 × 0.5 = **12979**, asserted not a multiple of 257 — precision an 8-bit pipeline cannot hold) and `boxBlur16` (neighbours 25700/25957 → **25786/25871**, downscaling only on demand to 100/101). Inputs never mutated; invalid gain/radius/fill rejected. |
| 3 | PNG improvements: palette (PLTE/tRNS) decoding and 16-bit decode/encode, fixtures with known pixels built independently | `imageCodec.ts` decoder generalized (shared unfilter parameterized by bytes-per-pixel). Palette: PLTE expansion with per-index tRNS alpha — hand-built fixture decodes to exact RGBA incl. alpha 128 on index 0; missing PLTE and out-of-range index are named errors; a Sub-filtered palette row (bpp=1) decodes exactly. 16-bit: hand-built depth-16 fixtures (RGBA filter-0 and Sub-filtered at bpp=8, grayscale, RGB) decode sample-exact via `decodePng16`; `encodePng16` output is walked structurally (chunk order, depth/type IHDR bytes) and decodes back exactly. 8-bit grayscale (0) and grayscale+alpha (4) decoding also landed. Plain `decodePng` refuses 16-bit files naming `decodePng16` — no silent precision loss. |
| 4 | JPEG: inspect; do not fake a codec if none exists; state the resulting state exactly | Inspected: no JPEG codec in the codebase and **no JPEG-capable library in `node_modules`** (no sharp, jimp, jpeg-js, pngjs — no image library at all besides this engine). State after Phase 50, exactly: the TypeScript engine **cannot decode or encode JPEG**; `importImage` now recognizes the JPEG signature and throws "JPEG image detected: the TypeScript engine has no JPEG codec (import supports PNG and BMP; JPEG is supported by the generated desktop app via System.Drawing)" — tested against JFIF header bytes, including that `detectFormat` still returns null. Nothing is stubbed or simulated; the generated C# app's System.Drawing support remains the only JPEG path. |
| 5 | ICC/profile handling: at minimum iCCP preservation or extraction, byte-exact; dropped color metadata listed | Both halves implemented: `extractPngIccProfile` (name + inflated payload, compression method enforced) and `encodePng(img, { iccProfile })` writing iCCP before IDAT, plus `decodePngWithProfile`. The preservation loop over a hand-built iCCP fixture is byte-exact for the payload (name `FakeRGB`, 132-byte fabricated profile) with chunk order asserted. Dropped-on-round-trip metadata is listed in `PHASE_50_PROGRESS.md` and the codec header: gAMA/cHRM/sRGB/text/time/physical-size chunks are not preserved; RGB/grayscale tRNS (transparent-color) is not applied (palette tRNS is). Profiles are carried as data only — never parsed or applied. |
| 6 | Color-accuracy tests; gamma handling stated plainly | Exact-value tests throughout: primaries through grayscale (76/150/29), 8→16 (65535/32896), 16→8, and the full 8→16→8 round trip; mid-gray 128 → gray 128 and → 32896 → 128. Gamma: the engine's working assumption — **all values are sRGB-encoded as stored and no operation linearizes** — is stated in `colorManagement.ts`, the codec header, and both Phase 50 docs, and pinned by the mid-gray identity test. No color-managed pipeline is claimed. |

## Known limitations

No JPEG codec in the TypeScript engine (decode or encode) — recognized and refused with the exact reason; the generated desktop app (System.Drawing) is the only JPEG path. No ICC-based color conversion: profiles are extracted and re-embedded byte-exact but never applied, and non-sRGB-profiled files are still treated as sRGB-encoded samples. No gamma linearization anywhere (the documented working assumption, consistent with Phases 19–49). Grayscale conversion discards alpha and color irreversibly (documented at the function and in the progress doc). Sub-8-bit PNG depths (1/2/4) and interlaced PNGs remain unsupported in both decoders. The project/layer model remains 8-bit RGBA: `GrayImage`/`PixelImage16` are working representations with conversions and codec paths, layers do not store them natively, Phase 47 filters do not run on 16-bit data (native 16-bit operations are gain and box blur), and PSD stays 8-bit. Ancillary PNG chunks other than PLTE/tRNS/iCCP-via-API are not preserved across decode→encode (full list in `PHASE_50_PROGRESS.md`). The HTTP routes and the generated C# desktop app do not expose Phase 50 features yet. Full detail in `PHASE_50_PROGRESS.md`.

## Acceptance

Phase 50 is ready for the owner's acceptance decision. Implemented and verified: the grayscale working representation, the 16-bit representation with two native 16-bit operations, full 8-bit PNG color-type decoding (palette with tRNS, grayscale, grayscale+alpha), 16-bit PNG decode/encode, grayscale PNG encode, and byte-exact ICC profile carriage. Stated as gaps, with reasons: JPEG (no codec or library exists), ICC application and gamma linearization (not implemented anywhere in the engine, by documented assumption), and native gray/16-bit layer storage (representations and codecs only in this phase).
