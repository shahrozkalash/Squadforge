## Requirement-by-requirement

| # | Requirement | Evidence |
| :--- | :--- | :--- |
| 1 | Action model: ordered `{operation id, params}` steps over a documented vocabulary (Phase 47 filters by registry id, Phase 19 adjustments, layer add/flatten or composite export, resize, PNG export settings), validated against the engine's own validators, rejected at definition/load time | The 14-op vocabulary is data (`ACTION_OPS` / `listActionOps()`), each op naming its engine entry point; coverage is asserted by test. Filter steps validate through `getFilterDescriptor` + `resolveFilterParams` (unknown id/name and out-of-range values throw; defaults are filled and stored resolved — a gaussian-blur step given only `sigma` ends up schema-complete). Thirteen invalid forms (unknown op, unknown filter, bad filter params, unknown step keys, saturation/opacity/blend/rotate/resize range violations, traversal export name, malformed shapes) plus malformed JSON all throw `Invalid action: …` from `validateAction`/`defineAction`/`parseAction`. An action whose *second* step is invalid leaves the project byte-unchanged — validation precedes the first step, so there are no mid-replay validation surprises. |
| 2 | Recording: a recorder that drives real engine calls on a live project and produces the action for exactly what was done | `ActionRecorder` methods each perform the engine operation on the live project and append the reproducing step (layers recorded by name, filter params recorded resolved). A six-step recording (box-blur, brightness/contrast, add-layer, fill-rect, set-opacity, export) replays on a fresh copy of the source to a byte-identical composite, and the replayed export buffer equals the recorder's own snapshot byte-for-byte. An out-of-range recorder call throws from the engine and records nothing. |
| 3 | Replay matches manual operations byte-exactly; actions serialize to JSON and back field-exactly (presets) | On a two-layer project, replay of the defined action equals the hand-driven sequence (applyFilter + adjustBrightnessContrast + addLayer + fillRect + setLayerOpacity) byte-exactly, with identical layer structure. Preset round trip: `parseAction(serializeAction(a))` deep-equals `a`, and re-serializing the loaded preset reproduces the identical JSON text. |
| 4 | Batch processing over multiple real input files, each output verified, per-file results reported individually | Four distinct fixture PNGs written to a temp dir are batch-inverted; the summary is `{4, done 4, failed 0, cancelled 0}`, every output file is decoded and compared byte-exactly against the expected inverted pattern, and each result carries its own input path, output path, status and null error, in input order. |
| 5 | Queue + progress + cancellation + errors: progress with per-file status, cancellation that stops new files (finished files stay done, final state says cancelled and how far), one file's failure does not abort the batch; deterministic async tests | Progress snapshots settle 1,2,3,4 across the four-file batch. A corrupt-bytes file and a missing file each land as `failed` with their error messages recorded (ENOENT visible for the missing one) while the good files before and after them complete: `{done 2, failed 2, cancelled 0}`. Cancellation triggered from the progress callback after two completions yields `{done 2, failed 0, cancelled 3}`: the two finished outputs are the only files in the output directory, unstarted files report `cancelled` with no output, and `job.progress()` agrees with the summary. No sleeps or timing races anywhere — cancellation is callback-driven and per-file work between awaits is synchronous. |
| 6 | Export queue: outputs written through a queue with configurable concurrency (honest default 1), drains in order with a `{done, failed, cancelled}` summary | `startBatch` is the queue: files start in input order through `concurrency` lanes (default 1), results remain in input order at any concurrency (verified at concurrency 2), and `job.done` resolves with the drain summary counts plus the full per-file results. Invalid actions and a zero concurrency are rejected synchronously before anything starts. An action with a BMP export step drives the batch output format, with per-input output names (the step's fixed name is deliberately not reused per file, so files cannot overwrite each other). |

## Known limitations

The vocabulary is the 14 listed operations — painting, selections, masks, groups, transforms, content layers and Phase 52 effect stacks are not recordable steps in this phase. Layer targeting is by (non-unique) name, resolving to the first match; engine ids are per-project UUIDs and cannot appear in a stored preset. Export settings are format + name only — the PNG encoder's sole option is an ICC profile (Phase 50), and binary profile data is deliberately not action data. Batch lanes interleave at file boundaries (decode/replay/encode are synchronous engine work), so concurrency overlaps file I/O rather than parallelizing one image; cancellation likewise takes effect between files, and a started file always finishes truthfully. Batch inputs are single images decoded by the existing codec (PNG/BMP), each becoming a one-layer project; project JSON and PSD are not batch inputs. The generated C# desktop app and the HTTP routes do not yet expose actions or batch processing. Full detail in `PHASE_53_PROGRESS.md`.
