## Known limitations

- **Windows first run is unverified.** The PixelForge window — mouse canvas events, panel rendering, visual layout, the undo/redo interaction, and now also the crash message box — has never executed anywhere. What has executed is the app's engine core and document model (the code every control calls) and its crash-report writer, headless on Linux. Installation on Windows is verified to the package-completeness level only.
- **The Linux package is not the graphics editor.** It is the Desktop Development Engine's Avalonia application, the only Linux GUI this architecture generates. No Linux build of PixelForge exists.
- **Both packages are framework-dependent and unsigned**: the user must install the .NET 8 runtime (Desktop Runtime on Windows) first, and OS first-run warnings (SmartScreen) are expected. No installer (MSI/MSIX/AppImage) is produced — the packages are plain archives with a README.
- **Crash reports are local files only** — nothing is transmitted anywhere; the user attaches a report to a bug report manually. The background-thread handler can only write on a best-effort basis while the process dies (`TryWriteReport` never throws; a failed write leaves no report).
- Observed platform edge (recorded, not fixed — scaffold behavior from Phase 36): if the per-user config home does not exist at all, .NET returns an empty `ApplicationData` path and the Linux app's state store falls back to a CWD-relative path. Real user machines have a config home; the release's install verification creates one, as Phase 36's test did.
- All standing limitations from Phases 56–59 remain in force (desktop-app scope: no layer groups in the app, rectangle selections only, scalar Speckle Tip, modelled brush pressure, PSD/TIFF refused in the app, JPEG quality pinned at 90; no GPU acceleration anywhere; parallel CPU opt-in with serial default).
