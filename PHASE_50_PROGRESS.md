# Phase 50 Progress — Professional Color Management (Graphics Editor)

Date: 2026-11-26
Baseline: local snapshot after Phase 49 (staged locally, **not pushed** — batched push is the owner's)
Status: **Implemented and verified locally.** Color management lands inside the existing engine: two new working representations in `server/imageEditor/types.ts` (`GrayImage`, `PixelImage16`), a new module `server/imageEditor/colorManagement.ts` with the conversions and the operations that run natively in 16-bit, and a widened PNG codec in `server/imageEditor/imageCodec.ts`. `imageCore.ts` is untouched — the Phase 19 adjustments, Phase 47 filters and everything built on them behave exactly as before. Acceptance is the owner's decision.

## The working assumption, stated plainly

Every sample in this engine is an **sRGB-encoded (gamma-encoded) value, exactly as stored** in the source file or produced by earlier phases. Nothing in the engine linearizes gamma — luminance, blending, filtering and compositing are all computed on the encoded values, which is the convention Phases 19–49 already follow. Phase 50 does not invent a color-managed pipeline on top of that: ICC profiles are *carried as data* by the PNG codec (below), never applied as transforms. A test pins the assumption: mid-gray 128 converts to gray 128, not to a linearized value.

## What was built

- **Grayscale as a first-class working representation** (`GrayImage`: one `Uint8ClampedArray` channel, the same representation masks/selections/brush tips already use). `rgbaToGrayscale` computes one Rec.601 luminance sample per pixel — 0.299/0.587/0.114, the weights the Phase 19 saturation/grayscale adjustments and the Phase 47 `luminance` helper already use — rounded with `Math.round`, the same rounding the adjustment path applies via `clamp255`. A test proves the representation and the Phase 19 `grayscale()` adjustment produce identical values on the same pixels, so there is one grayscale in this engine, not two. **Alpha is discarded by design** (the representation has no alpha channel) and RGB is used exactly as stored, never premultiplied — both facts are documented at the function and pinned by tests (a fully transparent red pixel converts to gray 76, not 0). `grayscaleToRgba` replicates channels with opaque alpha; gray→RGBA→gray is the identity for all 256 levels.
- **A genuine 16-bit workflow** (`PixelImage16`: RGBA `Uint16Array`, 0..65535 per channel). Conversion rules are exact and pinned: upscale is `v * 257`; downscale is `round(v / 257)`, the exact inverse for anything that came from 8-bit, so **8→16→8 is byte-exact for all 256 levels** (tested over a full-range image, not spot values). Two operations run natively in 16-bit in `colorManagement.ts` — they are not downscale/upscale sandwiches:
  - `applyGain16` multiplies RGB by a gain at 16-bit precision (alpha carried). Proof: 25957 × 0.5 = **12979**, a value no 8-bit upscale can represent (not a multiple of 257), asserted in tests along with clamping at 65535 and input immutability.
  - `boxBlur16` is a separable box blur over all four channels, accumulated in float and rounded once (edge replication, the Phase 47 convention). Proof: neighbours 25700 and 25957 blur to **25786 / 25871** — between 8-bit levels — and only quantize (to 100 / 101) when the caller explicitly downscales.
- **PNG decode widened to the full 8-bit color-type set** (`imageCodec.ts`). The Phase 19 decoder handled RGB (2) and RGBA (6); it now also handles **grayscale (0)**, **palette (3)** and **grayscale+alpha (4)**. Palette files get a real indexed→RGBA expansion: PLTE lookup plus tRNS applied per index (indices past the tRNS array are opaque); a missing PLTE and an out-of-range index are named errors, not guesses. The scanline unfilter was generalized to a shared helper parameterized by bytes-per-pixel, which is what makes 1-byte (gray/palette), 2-byte (gray+alpha) and 16-bit layouts all work — palette rows filtered with Sub at bpp=1 and 16-bit rows filtered with Sub at bpp=8 are both covered by hand-filtered fixtures. Palette/grayscale files at sub-8-bit depths (1/2/4) are still rejected with a named error.
- **16-bit PNG decode and encode**. `decodePng16` reads color types 0/2/4/6 at depth 16 into `PixelImage16` at full precision (grayscale replicates, missing alpha becomes 65535). `encodePng16` writes a real depth-16 RGBA PNG. The two directions are kept honest by construction: plain `decodePng` **refuses 16-bit files with an error naming `decodePng16`**, so 16-bit data is never silently reduced to 8-bit, and `decodePng16` refuses 8-bit and palette files by name.
- **Grayscale PNG encode**. `encodePngGrayscale` writes a real color-type-0 PNG from a `GrayImage` (the encoded file's IHDR type byte is asserted in tests, and it decodes back to the exact values).
- **ICC profile carriage**. `extractPngIccProfile` parses the iCCP chunk (Latin-1 name, compression method 0 enforced, zlib-inflated payload) and returns the profile bytes exactly as stored; `decodePngWithProfile` returns pixels + profile together; `encodePng` gained an optional `iccProfile` option that writes the iCCP chunk before IDAT (name validated: 1..79 Latin-1 chars, no NUL). The preservation loop — fixture → extract → re-encode → extract — is **byte-exact for the profile payload** (the zlib container is recompressed; the payload is not touched). Profiles are data only: no code in this engine parses or applies an ICC transform.
- **JPEG: the gap is documented, not filled with a fake.** There is no JPEG codec in this codebase and no JPEG library in `node_modules` (checked: no sharp/jimp/jpeg-js/pngjs or anything similar — the only image code is this engine). What Phase 50 adds is precision about the gap: `importImage` now recognizes the JPEG signature (FF D8 FF) and throws "JPEG image detected: the TypeScript engine has no JPEG codec (import supports PNG and BMP; JPEG is supported by the generated desktop app via System.Drawing)" instead of the generic unsupported-format error. JPEG encode does not exist either; `exportImage` still offers exactly PNG and BMP. The generated C# desktop app's System.Drawing JPEG support is unchanged and remains the only JPEG path.

## What a decode→encode round trip still drops (no silent loss — listed)

Plain `decodePng`/`encodePng` preserve pixels (and, via the explicit APIs, the ICC profile). Everything else ancillary is **not** preserved: gAMA, cHRM, sRGB, tEXt/zTXt/iTXt, tIME, pHYs and any unknown ancillary chunks are dropped on re-encode; tRNS for RGB and grayscale files (a single transparent-*color* spec, not per-pixel alpha) is not applied on decode (palette tRNS *is* applied, since it is per-index alpha). Encoded output is always plain samples — RGBA (type 6), grayscale (type 0) or 16-bit RGBA — plus the optional iCCP chunk. BMP has no color-management surface at all (samples are stored as-is, as before).

## Limitations (stated honestly)

- **No JPEG codec exists in the TypeScript engine** — neither decode nor encode — and Phase 50 does not change that (see above). It is not simulated or stubbed; the error names the situation and the one real JPEG path (the generated desktop app via System.Drawing).
- **No ICC-based color conversion anywhere.** Profiles are extracted and re-embedded byte-exact, never parsed or applied. An image whose embedded profile is not sRGB will be treated as sRGB-encoded samples regardless — that is the engine's working assumption, stated above, not a silent behavior.
- **Gamma is never linearized.** All math (luminance, blends, filters, the new 16-bit ops) runs on encoded values. This matches every earlier phase; changing it would alter existing verified results, so it is documented rather than "fixed".
- **Grayscale conversion discards alpha and color irreversibly**, and sub-8-bit PNG depths (1/2/4) and interlaced PNGs remain unsupported in both decoders. 16-bit palette PNGs do not exist in the PNG format and are refused if claimed.
- **The project/layer model is still 8-bit RGBA.** `GrayImage` and `PixelImage16` are working representations with conversions and codec paths; layers do not yet store them natively, and the Phase 47 filters do not run on 16-bit data (the two native 16-bit operations are gain and box blur). PSD import/export remains 8-bit only, as Phase 49 documented.
- The HTTP routes and the generated C# desktop app do not expose the Phase 50 representations or codecs yet.
