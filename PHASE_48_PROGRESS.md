## What was built

All in the existing engine — `types.ts` (model), `bitmapFont.ts` (glyph tables), `imageCore.ts` (operations).

- **Content layers** — `Layer` gains `kind: 'raster' | 'text' | 'shape'`, `text: TextLayerData | null`, `shape: VectorShapeData | null` and `contentTransform: number[] | null` (a row-major 3×3 placement matrix, the Phase 45 Mat3 form). A content layer's `image` is a deterministic render cache of its editable data; every mutator — `addTextLayer`, `addShapeLayer`, `updateTextLayer`, `updateShapeLayer`, the content transforms, and `deserializeProject` — re-renders the cache from the data. The data is the source of truth, so a loaded project is immediately editable and renders exactly what its data describes. Raster layers are unchanged in behavior (kind 'raster', null content fields).
- **Text layers** — the data carries the text (multi-line, split on '\n'), font id, nominal font size, alignment (left/center/right), letter spacing, line spacing, fill color, outline (whole-pixel width + color) and shadow (offset + box-blur radius + color), block origin and block width (0 = widest line). Layout is exact: glyph advance `6·scale + letterSpacing`, line advance `7·scale + lineSpacing`, each line aligned inside the block width from the whole-pixel-rounded origin. Rendering paints shadow (glyph coverage translated, then box-blurred with the Phase 47 edge-replication convention), then outline (coverage dilated by the Phase 45 max-morphology minus the coverage itself), then fill — all source-over through coverage maps. `measureTextBlock` exposes the layout (effective width/height, scale, line count); `textScaleFor` exposes the size snapping.
- **Built-in fonts, honestly** — text is set in the bitmap fonts of `bitmapFont.ts`; there is no system-font access in this engine and none is claimed. Two built-in typefaces ship: `pixel` (the Phase 19 5×7 set: A–Z with lowercase folding to uppercase, 0–9, basic punctuation `.,!?-_'":/()+`, space; unknown characters render the hollow-box fallback) and `pixel-bold` (a bold companion set materialized from the regular set by a 1px horizontal dilation — every set bit also sets its right neighbour — stored as its own glyph table; e.g. the stem of 'I' goes from row bits `0x04` to `0x06`). A nominal `fontSize` snaps to an integer bitmap scale: effective glyph height = `7 · round(fontSize/7)`, at least 7. Font selection is choosing between these two ids; unknown ids are rejected.
- **Text transformation** — `setContentTransform` sets a content layer's placement from a Phase 45 `Transform2D`; `transformContentLayer` composes one into it. The Phase 45 layer transforms were taught the same rule: `transformLayer`, `transformGroup`, `rotateLayerFree` and `perspectiveLayer` compose their warp into a content layer's placement matrix and re-render instead of warping the render cache (raster layers warp exactly as before; masks still warp with the layer). The data is never touched by a transform, so editing text after rotating it renders the new text in the rotated placement — proven by test 4.2, and a 90° `transformLayer` rotation of a text layer is byte-equal to `rotateImage` of its previous render (test 4.3).
- **Vector shapes** — `VectorShapeData` stores one shape per layer: rectangle, ellipse, line, polygon (vertex list) or path (cubic Bézier segment list), each with fill color, stroke color and stroke width (null fill/stroke or width 0 omits that paint), plus per-kind factories (`rectangleShape`, `ellipseShape`, `lineShape`, `polygonShape`, `pathShape`) that validate and deep-copy. Fills rasterize through the Phase 45 selection rasterizers (rect / inscribed-ellipse / even-odd polygon rules; a closed path fills its flattened polygon), strokes paint through the Phase 19 dot-stroke path along the outline (rectangle strokes follow the filled region's edge pixels; a closed path gains a straight closing segment). A line has no fill.
- **Bézier curves** — `cubicBezierPoint` evaluates the real cubic formula `B(t) = (1−t)³p0 + 3(1−t)²t·c1 + 3(1−t)t²·c2 + t³p1` (t outside [0, 1] rejected). `flattenBezierSegment` samples it at a fixed step count (default 16, endpoints included); `flattenPath` concatenates segments with joint points counted once. The symmetric segment (0,0),(0,10),(10,10),(10,0) passes exactly through (5, 7.5) at t = 0.5 and (1.5625, 5.625) at t = 0.25 — asserted with exact float equality, and a stroked path paints the pixels either side of the exact midpoint (5, 7.5).
- **Persistence** — the serialized format stays v2; `SerializedLayer` gains optional `kind` / `text` / `shape` / `contentTransform` fields holding the editable data field-for-field (deep-copied both ways, so history snapshots cannot alias live data). Files written before Phase 48 (fields absent, including v1 files) load every layer as a raster layer from its stored pixels. Present-but-corrupt content data is rejected, never silently loaded: unknown layer kind, missing text/shape payload, unknown font, unknown shape kind, a polygon with fewer than 3 points, or a content transform that is not 9 finite numbers all throw. On load, content layers re-render from their data (rendering is deterministic, so the composite is pixel-identical to the saved one — asserted byte-for-byte). Undo/redo needed no new code: `HistoryStack` snapshots go through serialize/deserialize, so they carry content layers (verified by test 7.4).

## Limitations (stated honestly)

- **Fonts are the two built-in bitmap typefaces only** — `pixel` and `pixel-bold`, one 5×7 grid, the documented character set above. There is no system-font rendering, no TrueType/OpenType loading, no anti-aliasing (glyph edges are hard bitmap edges, scaled blockily), and font size snaps to integer scales of the 7px grid. Lowercase folds to uppercase, as in the Phase 19 text tool.
- **The bold set is derived, not hand-drawn**: `pixel-bold` is the regular set emboldened by a documented 1px horizontal dilation rule, materialized as its own table.
- **Text layout is simple**: left-to-right lines split on '\n', aligned per line inside the block width; no wrapping, no justification, no per-character styling, no text-on-a-path. Letter/line spacing are uniform per layer. Outline width is whole pixels; shadow blur is a box blur whose radius is rounded to whole pixels, and shadow offsets are rounded to whole pixels at render.
- **Canvas operations desync content caches**: crop/resize/step-rotate of the whole project still operate on layer pixels (including content layers' render caches) and do not rewrite text/shape data or origins; a later content edit re-renders from the data at the project's current size, discarding the canvas op's effect on that layer. The Phase 45 transforms do not have this problem — they compose into placement.
- **Painting on a content layer paints its cache**: the Phase 19/44/46 tools operate on `layer.image`, so brush strokes on a text/shape layer modify the render cache and are discarded by the next content re-render. Content layers are for content, raster layers are for painting; nothing silently converts between them in this phase.
- **Shape model scope**: one shape per shape layer; path segments are expected to be continuous (each p0 = previous p1) — discontinuity is not rejected, it just renders as authored (fill uses the flattened point list as one polygon; stroke draws each segment separately plus the optional straight closing segment). Ellipse stroke is a parametric polyline through the Phase 19 dot path, so a width-1 ellipse stroke can be sparse at diagonal extremes; fills are exact. No gradient fills, no dash patterns, no shape boolean operations.
- **The generated C# desktop editor app** (`imageProjectGenerator.ts`, Phase 19) does not yet expose Phase 48 features — as with Phases 44–47, this phase covers the TypeScript engine.
