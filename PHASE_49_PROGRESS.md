## What was built

`importPsd(data): { project, warnings }` and `exportPsd(project): Buffer`, implementing the Adobe PSD format (signature `8BPS`, version 1 — the classic PSD, not the large-document PSB) from the specification, in TypeScript, with no new dependency (no PSD library exists in `node_modules`; Node's built-in `zlib` covers the ZIP compression variants). Nothing about the support is simulated: the parser walks the real binary sections and the writer emits them.

- **Header** — signature and version checked (`8BPS`, version 1; version 2 is rejected as PSB with a named error). Channels, dimensions, depth and color mode are read and enforced: only RGB (mode 3) at 8-bit depth is supported. CMYK, Lab, Grayscale, Indexed and the other modes, and 16/32-bit depths, throw named errors instead of producing a mangled project. Dimensions are sanity-capped (30000 per side per the spec, plus a total-pixel guard against corrupt headers).
- **Layer records** — bounding box (top/left/bottom/right), channel directory (id + data length), `8BIM` blend signature and key, opacity byte, clipping byte, flags byte, and the extra-data block: layer mask data (rectangle, default color, flags — including the "real" mask rectangle when the parameters flag is set), blending ranges (walked by length; their content is not modeled by this engine), the Pascal name, and the additional-info tagged blocks. The Unicode name (`luni`) is preferred over the Pascal name when present. Blend keys map to the engine's modes (`norm`, `mul `, `scrn`, `over`, `dark`, `lite`); an unknown key imports as `normal` **with a warning naming the key**. Opacity is the stored byte / 255 (the format quantizes opacity to 1/255). Visibility is flags bit 1 (set = hidden), clipping byte 1 maps to the Phase 44 `clipped` flag, and flags bit 0 (transparency protection) maps to `alphaLock`.
- **Groups** — section-divider records (`lsct`): folder records (types 1/2) become Phase 44 `LayerGroup`s with the record's name, opacity, visibility and blend key; the bounding divider (type 3) closes the innermost group. Records are stored top-to-bottom in the file, so import walks them bottom-to-top, which makes a folder record open its group and its divider close it; nesting falls out of a stack. A `pass` (pass-through) blend key on a group maps to `normal` with a warning, because this engine always composites a group into an isolated buffer. Unbalanced dividers are reported, not fatal.
- **Channel data** — decoded per channel after all records, in record order, honoring each channel's declared length (the reader resynchronizes to `start + length` after every channel, so one quirky channel cannot desync the file). All four compression forms are genuinely decoded: RAW (0), RLE/PackBits (1, per-row byte counts), ZIP (2) and ZIP-with-prediction (3, per-row byte deltas), via a hand-written PackBits codec and Node's `zlib`. R/G/B planes and the alpha channel (-1) are placed into a canvas-sized layer image at the layer's bounding-box offset (this engine's layers are canvas-sized — there is no layer-offset model — so the box position becomes pixel position; pixels falling outside the canvas are dropped, with a warning). A missing alpha channel means opaque inside the box. Spot/extra channels are skipped with a warning.
- **Layer masks** — the mask channel (-2, falling back to -3) is decoded at the mask rectangle's size and placed onto a canvas-sized Phase 44 mask at that rectangle, with the file's default color (0 or 255) outside it. A mask that was disabled in the source imports as enabled, with a warning (the engine has no disabled-mask state). Mask channel data without a mask rectangle is reported and not imported.
- **Merged composite** — a flattened PSD (no layer records) imports its merged image data section (RAW or RLE; all header channels, alpha from the 4th when present) as a single `Background` layer. ZIP-compressed merged data is reported rather than guessed at (the merged section carries no per-channel lengths to delimit the streams).
- **Unsupported-feature reporting** — the importer collects a `warnings` list; nothing it cannot preserve is dropped silently. Recognized additional-info keys produce named notes: Photoshop text data (`TySh` — the layer imports as raster pixels, not editable text), layer effects (`lfx2`/`lrFX`), adjustment-layer data (`brit`, `levl`, `curv`, `expA`, `blnc`, `hue2`, `hue `, `nvrt`, `mixr`, `grdm`, `phfl`, `post`, `thrs`, `selc`, `vibA`, `blwh`), fill-layer data (`SoCo`/`GdFl`/`PtFl`), smart objects (`SoLd`/`PlLd`), vector data (`vstk`), and fill opacity (`iOpa` ≠ 255). A layer with a bounding box but no pixel channels is imported as an empty layer with a warning.
- **Export** — writes a structurally valid version-1 PSD: header (4 merged channels), empty color-mode and image-resource sections, then the layer-and-mask section (layer records + RLE channel data + empty global mask info), then an RLE merged-composite section produced by the engine's own `composite()`. The stack is flattened to file order (top-to-bottom) with each group emitted as divider record, children, folder record, positioned at the group's lowest member — the engine's compositing rule. Records carry Pascal + `luni` names, opacity byte, visibility/clipping/alpha-lock flags, blend keys, blending ranges, and (when a layer has a mask) a -2 mask channel with the mask rectangle set to the layer bounds and default color 255. A layer's stored bounds are the bounding box of the pixels that carry data — any pixel with a nonzero byte (so transparent pixels that still carry RGB survive), plus any mask pixel that is not fully revealing — which makes the writer→reader path pixel-exact. Empty layers are stored with zero-area bounds and compression-word-only channels.
- **Documented export losses** (stated here and in the acceptance report, not hidden): Phase 48 text/shape content layers export as their rendered pixels and re-import as raster layers (PSD has no representation of this engine's content model that we could write honestly); group blend `normal` is written as `norm` because the engine has no pass-through mode to write as `pass`; opacity is quantized to 1/255 by the format itself.

## Limitations (stated honestly)

- **Not full Photoshop compatibility, and never claimed.** Supported: PSD version 1, RGB, 8-bit, the layer/group/mask/blend surface listed above. Everything else is either rejected with a named error (PSB, non-RGB color modes, 16/32-bit depth) or reported in `warnings` and dropped (effects, adjustments, fills, smart objects, vector data, text editability, spot channels, unknown blend keys, fill opacity).
- **Blend modes**: only the six engine modes map. Photoshop's other keys (dissolve, soft/hard light, dodge/burn, hue/saturation/color/luminosity, …) import as `normal` with a warning — the engine has no such modes to map them to.
- **Groups always isolate** in this engine, so a pass-through group changes compositing semantics on import (warned). Group masks and group effects are not imported (groups have no masks in this engine's model).
- **Layers are canvas-sized** in this engine: a PSD layer's bounding-box position becomes pixel placement on the canvas, content outside the canvas is dropped (warned), and re-export stores the data bounding box rather than the original box — a fully transparent border around a layer is not preserved as geometry (its pixels, including transparent ones carrying RGB inside the data box, are preserved exactly).
- **Masks**: one mask per layer (the -2/-3 channel); vector masks are not imported. The mask's own blend/opacity semantics beyond the grayscale data and default color are not modeled.
- **Text and shapes**: PSD text (`TySh`) imports as raster pixels only; this engine's content layers export as rendered pixels. Neither direction preserves editability across the format boundary.
- **ZIP-compressed merged data** in a flattened file is reported, not decoded (no per-channel lengths exist in that section to delimit streams); layered files are unaffected because layer channels carry lengths. Image resources (resolution, ICC profile, thumbnails) are skipped on import and written empty on export.
- **The HTTP routes** (`imageEditorRoutes.ts`) were not extended with PSD endpoints in this phase; PSD import/export is an engine-level API (`importPsd`/`exportPsd`), like the codecs beside it.
- **The generated C# desktop editor app** does not expose PSD import/export — as with Phases 44–48, this phase covers the TypeScript engine.
